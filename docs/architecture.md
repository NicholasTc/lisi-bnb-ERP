# Foundation architecture

**Requirements update — 2026-10-16:** [MVP v2](decisions/004-court-first-manual-qris.md) develops customer court ordering first; counter/pickup/dine-in follow in Phase 2. Keep the approved stack/modular monolith. Replace universal payment-before-preparation with court preparation while unpaid and official manual merchant verification before ordinary handover. No gateway/webhooks/automated refunds in this MVP. Payment-verification implementation is blocked until merchant access/evidence/timing and staff procedures are confirmed. UI must be bright, professional and app-like rather than exposing simulator/dashboard complexity in normal tasks. See the [updated plan](implementation-plan.md).

**Implemented architecture below — v1 through 2026-10-15:** Milestones 1–3; local demo ordering only, no deployment or real payment processing. Demo-only configuration, provider processing and database payment-eligibility guards described below are implementation history, not the target v2 policy. They need reviewed changes/new migrations before v2 can work; the subsequent V2-1 extension is documented below; the remaining payment/operations changes are not implemented. Real gateway adapter work is deferred, not a v2 launch prerequisite. Shared integrity/security controls remain required.

- One TypeScript/Next.js application. HTTP handlers translate requests; server services enforce identity, authorization and database rules. Tailwind supplies minimal accessible styling.
- PostgreSQL is authoritative. Drizzle schemas generate reviewed SQL migrations; schema push and automatic startup migrations are not used.
- Docker Compose runs separate local development and test PostgreSQL instances. Test scripts accept only the dedicated loopback test host/port/database/user and verify a database environment marker before changing data. Production database access is excluded from local scripts.
- Local database owners can apply migrations but have no superuser/create-role/create-database/replication privileges. Production runtime-versus-migration credentials remain a launch decision.
- Better Auth provides password hashing, cookie verification and database sessions. Public registration and unneeded auth endpoints are closed. Database-backed throttling is enabled in every environment.
- Session expiry is eight hours from creation with refresh/cache disabled. Better Auth does not document an idle timeout: a server policy checks the existing session's database `last_activity_at` before access. Thirty minutes idle invalidates/deletes the session. Passive identity checks do not refresh activity; explicit same-origin activity requests do. No new token system or session store.
- Database triggers serialize session creation/activity with employee disabling. Disabling deletes sessions atomically and blocks new sessions. Authorization reads current roles on every protected request; there is no implicit role hierarchy. Each module lists its explicitly approved roles.
- Public health responses expose only availability. Readiness checks connectivity, applied migrations and the environment marker. Structured error logs allow only safe codes/request IDs, never request bodies, passwords, cookies or raw database errors.
- Real payments remain unavailable. Explicit demo configuration/signing secrets are allowed only in development/test; production rejects demo mode/operations. Production configuration is documented/tested with synthetic values, not connected to production infrastructure.

See [data model](data-model.md), [foundation decision](decisions/001-foundation.md), [open questions](OPEN_QUESTIONS.md) and [run instructions](../README.md).

Catalog module: server services own input/permission checks and transactional catalog/audit writes. Public browsing returns only visible menu items and active directory records; authenticated editing has explicit owner/preparation permissions. Optimistic versions plus row locks reject conflicts. Client creation IDs deduplicate retries without background infrastructure. See [catalog decision](decisions/002-catalog.md).

Browser tests build and start the packaged Next.js application with `APP_ENV=test`, a separate `.next-test` directory and `tsconfig.e2e.json`. They cannot reuse the development server/build; avoiding a second development watcher prevents shared generated-type reload loops. `NODE_ENV=production` selects Next.js optimization only: database/auth/payment configuration remains isolated test configuration. Generated test output is ignored by source lint/version control.

Ordering services validate channel/permissions, canonical checkout inputs and authoritative catalog data. PostgreSQL advisory locks serialize first submissions by operation ID; order row locks serialize payment/cancel/refund transitions. Snapshot totals and ledger invariants also have database guards. Expiration uses database deadlines on every relevant action, not an in-memory timer.

Provider boundary: `demo-provider.ts` verifies independent-secret HMAC evidence; `demo-payments.ts` owns the durable simulation inbox and privileged test commands. The shared `payment-processing.ts` receives normalized, server-marked verified evidence and enforces financial/order rules. No HTTP body can manufacture that marker. A later real adapter must validate merchant authentication/identity and map provider IDs/events into this boundary; reviewed configuration/schema extensions and real-provider tests remain required. No real adapter is selected or implemented.

Guest resource access uses a random 256-bit private key, hashed on the server, with a 24-hour database expiry. Keys travel in URL fragments and POST bodies; no private lookup credentials appear in HTTP URLs. Guest browser drafts support immutable retries after lost responses; employee counter drafts use scoped session storage and clear on logout/expiry. This is not an employee session replacement. Production privacy/retention/CSP and assisted recovery remain launch decisions.

## V2-1 implemented extension — 2026-10-16

See [decision 005](decisions/005-court-ordering.md). Public court creation now uses the shared transactional order service with immutable `court_test` provenance, no payment deadline and `awaiting_preparation` eligibility while unpaid. Non-production availability is independent of the demo signing secret; production remains closed. Existing demo processing/ledger/inbox checks reject court-test records. Historical financial behavior stays protected by its original rules and regression tests. No manual payment verification, employee queue/claim execution or collection workflow exists yet.

Private status/cancel results are generation-checked when access fragments change, including late cancellation responses. New court drafts use a separate browser key from v1 checkout so an uncertain old payment-first draft is not silently reinterpreted. New public references are display identifiers, not authorization. UI recovery details are progressively disclosed and local-test limitations remain visible.
